# 需求处理 - PRD拆分与澄清

接收PRD文档,进行需求拆分和澄清,确保需求完整、一致、明确。

## 前置检查
1. 确认是否存在未完成工作流,可选恢复或重新开始
2. 自动初始化工作目录结构

## 执行步骤

### 1. 收集需求信息
- 用户描述需求 → 整理后保存到 `prd/original.md`
- 用户上传文件 → 保留在 `resources/`,同时提取到 `prd/original.md`
- 用户提供链接 → 获取内容并打包所有关联资源:
  - 主文档保存到 `resources/docs/`
  - 解析文档中的图片、附件、设计稿等资源引用
  - 下载所有资源到 `resources/images/`、`resources/files/`
  - 更新文档中的引用路径为本地相对路径
  - 整理到 `prd/original.md`

**Figma 设计稿处理**:

在收集需求过程中,主动询问用户是否有 Figma 设计稿:
```
是否有 Figma 设计稿?
[选项]
A. 是 - 我有 Figma 设计稿链接
B. 否 - 暂无设计稿或稍后提供
```

如果用户提供 Figma 链接:

**1. 检测已有拆分结果**

检查 `resources/figma.md` 是否存在:
- 如果存在,展示已有拆分结果,询问是否重新拆分/追加/使用现有
- 如果不存在,继续下一步

**2. 保存链接并询问拆分策略**

保存链接到 `prd/original.md` 的"设计稿"章节,然后询问:
```
检测到 Figma 设计稿链接。

是否立即进行页面拆分并获取截图?
[选项]
A. 是 - 立即运行 /spec.utils.figma-split 进行拆分,便于后续工作
B. 否 - 稍后手动运行 /spec.d2c 时再处理

💡 建议选择"是":
- 自动分析设计稿结构,识别所有页面/Frame
- 获取每个页面的截图,保存到 resources/screenshots/
- 生成 resources/figma.md 页面关联文档
- 在需求澄清时可参考具体页面截图
- 技术方案阶段可直接关联功能点与设计页面
```

**3. 调用 `/spec.utils.figma-split`**

如果用户选择"是",使用 SlashCommand tool 调用:
```
/spec.utils.figma-split
```
传入上下文:用户提供的 Figma URL

工具将自动完成:
- 调用 Figma MCP 获取设计稿结构(使用 `figma_get_frame_links`)
- 分析页面/Frame 数量
- 询问用户拆分策略(拆分/整体/自定义)
- 获取页面截图(拆分模式下)
- 生成 `resources/figma.md` 页面关联文档
- 保存截图到 `resources/screenshots/`

**4. 拆分完成后的输出**

拆分完成后会生成:
```
resources/
├── figma.md                              # Figma 页面关联文档
├── screenshots/                            # Figma 页面截图目录
│   ├── 01-{页面名称}-{nodeId}.png
│   ├── 02-{页面名称}-{nodeId}.png
│   └── ...
```

在终端展示拆分结果:
```
✅ Figma 页面拆分完成!
- 拆分策略: {split/whole/custom}
- 页面数量: {N} 个
- 截图数量: {N} 个
- 关联文档: resources/figma.md

📋 已记录页面与功能点关联:
1. {页面名称1} - ✅ 截图已保存
   - 关联功能: {功能名称1}
   - Figma 链接: {URL with node-id}
   - 截图: resources/screenshots/01-{页面名称1}.png

2. {页面名称2} - ✅ 截图已保存
   - 关联功能: {功能名称2}
   - Figma 链接: {URL with node-id}
   - 截图: resources/screenshots/02-{页面名称2}.png
...

现在可以继续需求收集流程。
```

**5. 继续需求收集流程**

拆分完成后:
- 在需求澄清阶段可参考 `resources/screenshots/` 中的截图
- 在技术方案阶段读取 `resources/figma.md` 关联功能点与设计页面
- 后续如需更多设计详情(组件结构、代码),运行 `/spec.d2c`

**6. 如果用户选择"否"**

记录到 README 的待办事项:
```
⏳ 待完成:
- [ ] Figma 设计稿拆分 (稍后运行 /spec.d2c 时处理)
```

自动更新README,记录执行日志

### 2. 项目上下文分析(读取代码知识库)

**目的**: 了解项目实际结构,为需求拆分提供上下文，避免重复定义现有功能

**执行**:
1. 检查 `.spec/knowledge/` 是否存在:
   - 不存在 → 提示用户先运行 `/spec.init`
   - 存在 → 继续分析

2. 并行读取知识库文档(使用 Task tool 并行):
   - `architecture.md`: 项目类型、技术栈、目录结构
   - `pages.md`: 现有页面/路由（仅页面名称和功能描述）
   - `components.md`: 现有组件体系（仅组件名称和用途）
   - `apis.md`: 现有API接口（仅接口名称和功能描述）

3. 生成 `prd/project-context.md`,包含:
   ```markdown
   # 项目上下文分析

   ## 项目特征
   - 项目类型: {React SPA / Next.js / Vue Admin / 后端API / 微前端 / ...}
   - 技术栈: {主要框架和库}
   - 组织方式: {按功能/按路由/按层级}

   ## 现有资源盘点（名称级别，不涉及代码）
   - 页面数量: {N}个
     - 示例: 用户列表页、订单详情页、数据看板等
   - 组件数量: {M}个
     - 示例: 用户信息卡片、数据表格、搜索框等
   - 接口数量: {K}个
     - 示例: 用户查询接口、订单创建接口、数据统计接口等

   ## 拆分维度推荐

   基于项目类型,推荐按 **{页面/模块/功能/接口}** 拆分

   **推荐理由**:
   - {理由1: 如"项目采用页面路由结构,按页面拆分更清晰"}
   - {理由2: 如"现有组件可复用,按功能模块拆分减少重复"}

   ## 相关现有模块（仅列出名称，避免重复定义）
   - 现有页面: {列出相关页面名称}
   - 现有组件: {列出可能复用的组件名称}
   - 现有接口: {列出相关接口名称}

   💡 注意：此分析仅用于识别现有资源，拆分时避免重复定义已有功能
   ```

### 3. 需求拆分(基于项目上下文和Figma设计)

**拆分策略** (基于步骤2的分析):

**按项目类型智能拆分**:
- Next.js/Nuxt.js应用 → 按页面路由拆分,对齐 `pages.md`
- React组件库 → 按组件拆分,对齐 `components.md`
- Vue Admin系统 → 按菜单模块拆分,参考 `pages.md` + 菜单配置
- 后端API服务 → 按接口分组拆分,对齐 `apis.md`
- 微前端应用 → 按子应用拆分,参考 `architecture.md`
- 多项目协同 → 按工程项目拆分, 参考 `/spec.multi-project`

**拆分原则**:
1. 对齐现有架构: 拆分结果应与现有目录结构、页面组织方式一致
2. 复用现有模块: 优先识别可复用的现有页面/组件/API
3. 最小改动范围: 相关功能聚合,减少跨模块依赖
4. 合理粒度: 单个子需求不超过3个页面或5个组件

**拆分执行**:

**前置步骤: 读取 Figma 页面关联**
- 检查 `resources/figma.md` 是否存在
- 如果存在,读取所有已拆分的 Figma 页面信息:
  - 页面名称
  - 截图路径
  - Figma 链接
- 在拆分时可将功能点与对应的 Figma 页面关联

**拆分每个子需求时包含**:
- **所属模块/页面**(关联现有模块名称，非代码路径)
- **关联的 Figma 页面** (如果有):
  - Figma 页面名称
  - Figma 截图路径: `resources/screenshots/XX-{页面名称}.png`
  - Figma 链接 (含 node-id, 用于后续实施时精确定位图层)
  - 用户上传截图路径 (如果有): `resources/images/XX-{文件名}.png`
- 功能描述
- 交互流程
- 边界条件
- UI元素 (参考 Figma 截图，描述视觉效果和交互行为，不涉及实现)
- **现有资源识别**: 列出可能复用的现有组件/页面/接口名称 (从知识库提取，仅名称不涉及代码)

💡 **重要**: 拆分阶段聚焦业务功能和交互细节，不涉及代码实现、数据库字段、接口定义等技术细节

**在生成拆分文档前，向用户确认关联关系**:

生成 `prd/questions/figma-mapping.md` 文档，展示每个子需求与 Figma 页面的建议关联：

```markdown
# Figma 页面与功能点关联确认

> 请对比截图，确认或调整以下关联关系，确认后回复"已确认"

## 子需求 1: {功能名称}

### 📸 截图对比

**左侧：用户提供的截图** (如果有)

![用户截图](../resources/images/{文件名}.png)

**右侧：Figma 设计稿截图**

![Figma截图](../resources/screenshots/01-{页面名称}.png)

### 📋 关联信息

- **建议关联的 Figma 页面**: {页面名称}
- **Figma 链接**: {URL with node-id} (用于精确定位图层)
- **关联理由**: {根据功能描述和页面名称自动推断}

### ✅ 确认选项

- [ ] 确认关联正确 - 用户截图和 Figma 设计稿对应同一功能
- [ ] 需要调整 (请说明关联到哪个页面): ___________
- [ ] 无需关联 Figma
- [ ] 用户截图和 Figma 不一致 (请说明): ___________

---

## 子需求 2: {功能名称}
{同上格式}

---

## 📌 说明

- **用户截图**: 从 PRD 文档或需求描述中提取，可能是现状、参考或预期效果
- **Figma 截图**: 来自设计稿，反映最新的设计方案
- **对比目的**: 确认功能点与设计稿的对应关系，识别差异
- **Figma 链接**: 包含 node-id，后续实施时可精确定位到具体图层
```

**生成确认文档的关键步骤**:
1. 使用 Read 工具读取用户上传的截图 (如果有)
2. 使用 Read 工具读取 Figma 截图
3. 在确认文档中以并排对比的方式展示两种截图
4. 自动推断关联理由 (基于功能描述和页面名称的语义匹配)
5. 提供多个确认选项，包括"截图不一致"的情况

**文档命名规范**:
- 格式: `prd/split/{优先级}-{模块名}-{功能名}.md`
- 示例:
  - `P0-user-auth-login.md` (高优先级，必须实现)
  - `P1-user-profile-edit.md` (中优先级，建议实现)
  - `P2-theme-dark-mode.md` (低优先级，可选实现)
- 优先级定义:
  - **P0**: 核心功能，必须实现，阻塞上线
  - **P1**: 重要功能，建议实现，影响体验
  - **P2**: 次要功能，可选实现，锦上添花

**拆分文档格式** (`prd/split/{优先级}-{模块名}-{功能名}.md`):
```markdown
# {功能名}

- **所属模块**: {模块名/页面路径}
- **优先级**: P0/P1/P2

## 设计稿关联
- **Figma 页面**: {页面名称}
- **Figma 截图**: `resources/screenshots/XX-{页面名称}.png`

  ![Figma设计](../resources/screenshots/XX-{页面名称}.png)

- **Figma 链接**: {URL with node-id} (用于后续实施时精确定位图层)
- **用户上传截图**: `resources/images/XX-{文件名}.png` (如果有)

  ![用户截图](../resources/images/XX-{文件名}.png)

## 功能描述
{详细描述，结合 Figma 截图理解 UI 设计}

## 交互流程
{步骤描述，参考 Figma 截图中的交互元素}

## 边界条件
{边界说明}

## UI元素 (基于 Figma 截图)
{UI描述，直接引用 Figma 截图中的具体元素和样式}

## 现有资源识别
- **现有组件**: {列出可能复用的组件名称，如"用户信息卡片"、"数据表格"等}
- **相关页面**: {列出相关的现有页面名称，如"用户列表页"、"详情页"等}
- **关联接口**: {列出相关的现有接口名称，如"用户查询接口"、"数据统计接口"等}

💡 说明：此清单仅识别现有资源，避免重复定义，不涉及具体实现
```

保存到 `prd/split/{优先级}-{模块名}-{功能名}.md`

**按优先级组织**:
- 拆分完成后，子需求按优先级排序 (P0 → P1 → P2)
- 文件名包含优先级前缀，便于识别和实施
- 在汇总清单中按优先级分组展示

**Figma 关联确认**:
- 生成拆分文档后,如果存在 Figma 设计稿,生成 `prd/questions/figma-mapping.md`
- 在确认文档中展示每个子需求建议关联的 Figma 页面和截图
- 使用 Read 工具读取 Figma 截图,在确认文档中以图片形式展示
- 用户确认或调整关联关系后,更新拆分文档

**性能优化**: 如果子需求 > 3个,使用 Task tool 派发多个 agent 并行拆分,每个 agent 处理1-2个子需求

### 3.5 识别纯前端改动(快速通道)

**目的**: 识别不依赖后端的纯前端改动，提供快速通道跳过技术方案阶段

**识别标准**:

纯前端改动通常包括：
- ✅ 文案修改（提示语、标题、按钮文字等）
- ✅ 样式调整（颜色、字体、间距、布局等）
- ✅ UI微调（显示/隐藏元素、排序、格式化等）
- ✅ 前端配置修改（常量、枚举值、默认值等）
- ✅ 前端路由调整
- ✅ 静态资源替换（图标、图片等）

**排除标准**（以下不属于纯前端改动）:
- ❌ 需要新增/修改后端接口
- ❌ 需要新增/修改数据库字段
- ❌ 涉及业务逻辑变更
- ❌ 需要后端数据支持
- ❌ 涉及权限/认证逻辑

**执行流程**:

1. **分析所有子需求**，标记哪些是纯前端改动

2. **生成快速通道清单** (`prd/fast-track-candidates.md`):
   ```markdown
   # 纯前端改动快速通道清单

   以下需求识别为纯前端改动，可直接进入代码修改阶段：

   ## 🚀 快速通道候选（无需技术方案）

   ### 1. {功能名称} - 文案修改
   - **改动类型**: 文案修改
   - **改动范围**: {页面/组件路径}
   - **改动内容**: {具体改动描述}
   - **依赖**: 无后端依赖
   - **复杂度**: 低
   - **预估时间**: < 30分钟

   ### 2. {功能名称} - 样式调整
   - **改动类型**: 样式调整
   - **改动范围**: {页面/组件路径}
   - **改动内容**: {具体改动描述}
   - **依赖**: 无后端依赖
   - **复杂度**: 低
   - **预估时间**: < 1小时

   ---

   ## 📋 常规流程需求（需要技术方案）

   ### 3. {功能名称} - 业务逻辑变更
   - **改动类型**: 业务逻辑
   - **原因**: 依赖后端新增接口/字段
   - **继续**: 正常进入技术方案阶段
   ```

3. **询问用户确认**:
   ```
   检测到 {N} 个纯前端改动候选项。

   这些改动不依赖后端，可以快速处理：
   1. {功能名称} - 文案修改
   2. {功能名称} - 样式调整
   ...

   是否启用快速通道？
   [选项]
   A. 是 - 直接为这些改动生成代码改动清单，跳过技术方案阶段
   B. 否 - 所有需求统一进入技术方案阶段
   C. 自定义 - 我来选择哪些走快速通道（输入序号，如 1,2）

   💡 快速通道优势：
   - 节省时间：跳过技术方案，直接修改代码
   - 降低复杂度：无需设计接口、数据流
   - 快速上线：简单改动快速完成
   ```

4. **处理用户选择**:

   **选择 A (全部快速通道)**:
   - 将快速通道候选项标记为 `fast-track: true`
   - 保存到 `prd/fast-track-approved.md`
   - 这些需求跳过 `/spec.feat-tech`，直接进入 `/spec.code`
   - 在代码生成阶段会生成详细的改动清单

   **选择 B (全部常规流程)**:
   - 所有需求继续正常流程
   - 标记 `fast-track: false`

   **选择 C (自定义)**:
   - 解析用户输入的序号
   - 标记选中的需求为快速通道
   - 其他需求走常规流程

5. **更新需求文档**:

   在每个拆分文档 (`prd/split/{功能名}.md`) 的基本信息中添加：
   ```markdown
   ## 基本信息
   - **快速通道**: ✅ 是（纯前端改动，无后端依赖）/ ❌ 否（需要技术方案）
   - **改动类型**: 文案修改 / 样式调整 / 业务逻辑 / ...
   - **后端依赖**: 无 / 需要新增接口 / 需要修改字段
   ```

### 4. 需求预分析与澄清(并行处理)

**注意**: 快速通道需求可以跳过本阶段，直接进入代码生成

**重要原则**: 聚焦"做什么"(What)，不涉及"怎么做"(How)。避免询问技术实现细节。

**执行流程**:

#### 4.1 并行分析所有子需求

使用 Task tool 派发多个 agent,每个 agent 分析1-2个子需求:
- 读取拆分后的子需求文档
- 读取相关的知识库文档(components/apis/pages)
- 从三个维度评估需求质量(完整性/一致性/明确性)
- 生成该子需求的澄清问题(仅针对真正缺失/矛盾的地方)

**评估优先级**:

**🔥 P0 - 必须澄清(阻塞开发)**:
1. **功能完整性**: 功能是否有遗漏？业务流程是否闭环？
2. **逻辑正确性**: 业务规则是否有矛盾？是否存在逻辑冲突？
3. **可实现性**: 数据流是否完整？依赖关系是否明确？

**⚡ P1 - 建议澄清(影响质量)**:
4. **场景覆盖**: 异常场景、边界条件是否考虑？
5. **业务明确性**: 触发条件、预期结果是否清晰？

**📋 P2 - 后续细化(不阻塞开发)**:

## 注意事项

### 核心原则
1. **知识库优先**: 必须先读取 `.spec/knowledge/` 了解项目结构，避免重复定义现有功能
2. **聚焦功能本身**: 需求阶段只关注"做什么"(What)，不涉及"怎么做"(How)和代码实现
3. **现有资源识别**: 识别可能复用的组件/页面/接口名称，但不涉及具体代码
4. **优先级标注**: 所有拆分文档和澄清文档文件名必须包含优先级前缀 (P0/P1/P2)
5. **快速通道识别**: 主动识别纯前端改动（文案、样式等），提供快速通道跳过技术方案
6. **并行处理**: 子需求 > 3个时,使用 Task tool 派发多个 agent 并行处理,显著提速
7. **智能过滤**: 只针对真正有问题的地方提问,无问题的直接标注"✅ 无问题"
8. **批量确认**: 所有问题汇总到一个文档,避免多次往返

### 快速通道（重要）
9. **识别纯前端改动**: 在需求拆分后，主动识别不依赖后端的纯前端改动
   - ✅ 适用：文案修改、样式调整、UI微调、前端配置、静态资源替换
   - ❌ 排除：需要后端接口、数据库字段、业务逻辑变更、后端数据支持
   - 🚀 优势：跳过技术方案，直接生成代码改动清单，快速上线
   - 📋 输出：生成 `prd/fast-track-approved.md`，直接运行 `/spec.code`

### 澄清优先级（重要）
10. **聚焦功能本身**: 需求澄清优先处理功能遗漏/未闭环/逻辑错误,不过早陷入体验细节
   - 🔥 **P0 - 必须澄清**: 功能完整性、逻辑正确性、可实现性（阻塞开发）
   - ⚡ **P1 - 建议澄清**: 场景覆盖、业务明确性（影响质量）
   - 📋 **P2 - 后续细化**: 用户体验、业务合规（不阻塞开发）
   - **只针对 P0、P1 问题提问**, P2 问题标注"建议后续细化"
   - **注意**: 快速通道需求可跳过澄清阶段

### 边界定义
11. **聚焦业务需求**: 需求澄清阶段专注于"做什么"(What)，不讨论"怎么做"(How)
   - ✅ 询问：功能遗漏、流程闭环、逻辑矛盾、数据流、关键场景
   - ❌ 避免：接口定义、字段结构、组件选型、状态管理、实现方案、代码细节
   - ❌ 往后放：Loading 动画、权限粒度、审计格式等 P2 细节
   - 现有资源识别只列名称，不贴代码
   - 技术实现细节留给 `/spec.feat-tech` 阶段处理

### 实施细节
12. **文档命名规范**: 优先级必须作为文件名前缀
   - ✅ 正确: `P0-user-auth.md`, `P1-profile-edit.md`, `P2-theme-switch.md`
   - ❌ 错误: `user-auth.md`, `user-auth-P0.md`, `0-user-auth.md`
   - 优先级定义清晰: P0 (必须) / P1 (建议) / P2 (可选)
   - 按优先级排序展示: P0 需求优先实施
13. **路径引用规范**: 区分远程地址和本地文件路径
   - **本地文件**: 使用**基于需求目录根的相对路径**，不使用绝对路径
     - 需求目录根为: `.spec/feature/{YYYY-MM-DD}/`
     - ✅ 正确: `prd/clarified/user-auth.md` (基于需求目录根)
     - ✅ 正确: `resources/figma/screenshots/01-page.png` (基于需求目录根)
     - ✅ 正确: `prd/split/user-auth.md` (从 clarified 引用 split)
     - ❌ 错误: `/Users/xxx/.spec/feature/2024-01-01/prd/clarified/user-auth.md`
     - ❌ 错误: `/absolute/path/to/file.md`
   - **远程地址**: 可以使用完整的绝对 URL
     - ✅ 正确: `https://www.figma.com/design/xxx?node-id=123-456` (Figma 链接)
     - ✅ 正确: `https://example.com/api/docs` (API 文档)
     - ✅ 正确: `https://docs.example.com/guide` (在线文档)
   - 确保文档在不同环境/用户下都能正确引用
14. 所有自动化操作参考 `.claude/internal/workflow-utils.md`
15. `resources/` 目录保存原始文件不修改,按类型分类存储
16. 资源文件命名规则: `{timestamp}_{原始文件名}`,避免冲突
17. 如有Figma链接,使用相关工具获取设计信息
18. 下载资源失败时记录在日志中,不阻塞流程
