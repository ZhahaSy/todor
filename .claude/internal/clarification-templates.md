# 澄清问题模板

本文档提供需求澄清和技术方案确认的标准化模板,重点关注前端技术。

## 一、需求澄清问题模板

### 模板说明
- 使用markdown格式的checkbox
- 【必答】表示必须回答的问题
- 【可选】表示可选回答的问题
- 提供多个选项供用户勾选
- 留空白处供用户补充说明

---

```markdown
### 【必答】组件技术选型

已识别需使用: {列出组件列表}
- [ ] 确认使用以上组件

```

## 三、使用指南

### 3.1 需求澄清阶段使用

1. **生成问题清单**:
   - 分析需求后,选择合适的模板组合
   - 根据具体需求填充模板中的占位符
   - 保存到 `prd/questions/{功能名}-questions.md`

2. **前端侧重点**:
   - 组件技术选型(1.1)必选
   - 交互细节澄清(1.2)必选
   - 样式实现方案(1.3)根据需求
   - 数据流设计(1.4)涉及数据交互时必选
   - 联动逻辑影响(1.5)修改现有功能时必选

3. **生成方式**:
   - 优先生成文档让用户填写
   - 简单问题可用命令行交互
   - 给用户充分思考时间

### 3.2 技术方案阶段使用

1. **收集技术信息**:
   - 使用模板2.1收集前端技术栈信息
   - 保存到 `tech/questions/tech-info.md`

2. **改动点确认**:
   - 梳理完改动点后,使用模板2.2生成确认文档
   - 保存到 `tech/questions/change-confirmation.md`
   - 重点关注:
     - 组件改动影响(必查)
     - 联动逻辑检查(必查)
     - API和状态管理改动
     - 样式影响范围

3. **确认流程**:
   - 生成文档后等待用户确认
   - 用户可以在文档中直接标注修改意见
   - 根据反馈调整方案后重新生成确认文档

### 3.3 模板定制建议

1. **根据项目特点调整**:
   - 技术栈固定的项目可以简化技术选型问题
   - 规范完善的项目可以减少某些确认项
   - 复杂项目可以增加更多检查项

2. **根据团队习惯调整**:
   - 调整问题的表述方式
   - 调整选项的详细程度
   - 添加团队特有的确认项

3. **持续优化**:
   - 记录常见的遗漏问题
   - 完善模板覆盖更多场景
   - 简化冗余的确认项

## 四、最佳实践

### 4.1 问题设计原则

1. **选择题优于开放题**:
   - 提供明确的选项让用户勾选
   - 减少用户思考成本
   - 便于快速确认

2. **必答与可选分离**:
   - 明确标注【必答】和【可选】
   - 避免用户漏答关键问题
   - 可选问题不阻塞流程

3. **留补充空间**:
   - 在选项后留 "补充说明" 空白
   - 允许用户提供更多上下文
   - 不限制用户的表达

### 4.2 前端侧重点

1. **组件层面**:
   - 现有组件复用 vs 新建
   - 组件的影响范围
   - 公共组件的设计

2. **交互层面**:
   - 用户操作流程
   - 反馈机制(loading/toast/modal)
   - 边界case处理

3. **数据层面**:
   - 数据流向
   - 状态管理
   - API集成
   - 缓存策略

4. **联动层面**(重点):
   - 组件间依赖
   - 功能间影响
   - 历史逻辑检查

### 4.3 时间记录规范

所有文档中的时间记录必须精确到时分秒:
- 格式: `YYYY-MM-DD HH:mm:ss`
- 示例: `2025-12-12 17:30:45`
- 用途: 生成时间、确认时间、修改时间
