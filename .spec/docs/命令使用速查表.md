# 命令使用速查表

SDD AI 出码工作流的详细命令参考手册

## 📋 命令总览

| 命令 | 说明 | 耗时 | 阶段 |
|------|------|------|------|
| `/spec.init` | 初始化代码知识库 | 2-5分钟 | 准备 |
| `/spec.feat-prd` | 需求拆分与澄清 | 10-20分钟 | 需求 |
| `/spec.feat-tech` | 技术方案设计 | 15-30分钟 | 设计 |
| `/spec.code` | 生成项目代码 | 5-15分钟 | 开发 |
| `/spec.test` | 生成测试代码 | 5-10分钟 | 测试 |
| `/spec.review` | 代码审查 | 3-5分钟 | 审查 |
| `/spec.archive` | 归档与知识库更新 | 2-3分钟 | 归档 |

## 🔧 详细命令说明

---

### `/spec.init` - 初始化代码知识库

**用途**: 扫描现有代码，建立项目知识库

**使用场景**:
- ✅ 项目首次使用本工作流
- ✅ 架构发生重大变更
- ✅ 知识库内容过时需要重建

**执行流程**:
```
1. 扫描项目代码结构
2. 分析组件/API/函数/页面
3. 提取编码规范和架构设计
4. 生成知识库文档
```

**产出文件**:
```
.spec/knowledge/
├── components.md          # 组件清单和使用说明
├── apis.md               # API接口清单
├── functions.md          # 工具函数清单
├── pages.md              # 页面/路由清单
├── coding-standards.md   # 编码规范总结
└── architecture.md       # 架构设计说明
```

**示例**:
```
用户: /spec.init
AI: 开始扫描项目代码...
AI: 发现 15 个组件
AI: 发现 8 个API
AI: 发现 23 个工具函数
AI: ✅ 知识库初始化完成
```

**注意事项**:
- ⚠️ 首次执行耗时较长（2-5分钟）
- ⚠️ 大型项目可能需要更长时间
- 💡 建议在项目稳定后执行
- 💡 知识库会随着归档自动增量更新

---

### `/spec.feat-prd` - 需求拆分与澄清

**用途**: 收集PRD，拆分需求，澄清不明确的地方

**使用场景**:
- ✅ 开始新需求开发
- ✅ 需求不够明确需要澄清
- ✅ 复杂需求需要拆分

**执行流程**:
```
1. 创建需求目录 .spec/feature/{YYYY-MM-DD}/
2. 询问并收集PRD文档
3. 询问是否有Figma设计稿
4. 分析PRD并拆分子需求
5. 为每个子需求提出澄清问题
6. 根据回答生成明确的需求文档
```

**交互示例**:
```
AI: 请提供你的PRD文档（粘贴文本/文件路径/链接）
用户: [提供PRD]

AI: 是否有Figma设计稿？
用户: https://figma.com/...

AI: 🤔 我有以下问题需要澄清：
    1. xxx功能是否需要支持xxx？
    2. xxx的默认值是什么？
用户: [回答问题]

AI: ✅ 需求文档已保存
```

**产出文件**:
```
.spec/feature/{date}/
├── README.md              # 需求总览
└── prd/
    ├── original/          # 原始PRD
    │   ├── prd.md
    │   └── figma.md
    └── clarified/         # 澄清后的需求
        ├── req-1.md       # 子需求1
        └── req-2.md       # 子需求2
```

**提示**:
- 💡 PRD越详细越好
- 💡 Figma设计稿能大幅提升准确度
- 💡 认真回答澄清问题
- 💡 不确定时可以要求AI给建议

### `/spec.feat-tech` - 技术方案设计

**用途**: 基于需求和现有规范，设计详细的技术实现方案

**使用场景**:
- ✅ 需求澄清完成后
- ✅ 需要设计实现方案
- ✅ 需求变更需要重新设计

**执行流程**:
```
1. 询问项目类型（新项目/迭代项目）
2. 读取需求文档
3. 读取代码知识库
4. 生成技术方案概要
5. 梳理具体改动点（新建/修改）
6. 为每个改动点生成代码片段
7. 确认方案并保存
```

**交互示例**:
```
AI: 这是新项目还是迭代项目？
    - 新项目: 使用最新最佳实践
    - 迭代项目: 遵循现有规范
用户: 迭代项目

AI: [生成技术方案]
AI: 📝 技术方案概要:
    - 新建 3 个文件
    - 修改 2 个文件
    详细内容见: tech-solution.md

AI: 请确认方案
用户: 确认

AI: ✅ 技术方案已保存
```

**产出文件**:
```
.spec/feature/{date}/tech/
├── tech-solution.md       # 技术方案概要
└── modifications/         # 改动点详情
    ├── new-Login.tsx.md   # 新建：登录组件
    ├── modify-routes.ts.md # 修改：路由配置
    └── ...
```

**改动点文档格式**:
```markdown
# 新建文件: src/components/Login.tsx

## 文件说明
用户登录组件

## 代码片段
\```tsx
import React from 'react';
// ... 完整代码片段
\```

## 依赖
- react
- axios
```

**提示**:
- 💡 新项目选择"新项目"获得最新实践
- 💡 迭代项目选择"迭代项目"保持一致性
- 💡 仔细审查改动点是否合理
- 💡 发现问题可以直接修改改动点文档

### `/spec.code` - 生成项目代码

**用途**: 根据技术方案自动生成所有代码

**使用场景**:
- ✅ 技术方案确认后
- ✅ 修改改动点需要重新生成
- ✅ 只更新部分文件

**执行流程**:
```
1. 读取技术方案
2. 读取所有改动点文档
3. 对于新建文件:
   - 生成完整代码
   - 使用Write工具创建
4. 对于修改文件:
   - 读取原文件
   - 定位修改位置
   - 使用Edit工具精确修改
5. 生成代码生成报告
```

**示例**:
```
AI: 开始生成代码...
AI: ✅ 新建: src/components/Login.tsx
AI: ✅ 修改: src/routes/index.ts
AI: ✅ 代码生成完成
AI: 详细报告: .spec/feature/{date}/code-generation-report.md
```

**产出文件**:
- 项目代码文件（新建/修改）
- `.spec/feature/{date}/code-generation-report.md`

**代码生成报告内容**:
```markdown
# 代码生成报告

## 新建文件 (3个)
1. src/components/Login.tsx
2. src/components/LoginForm.tsx
3. src/api/auth.ts

## 修改文件 (2个)
1. src/routes/index.ts
2. src/App.tsx

## 依赖变更
新增依赖: axios

## 配置变更
无
```

**验证步骤**:
```bash
# 1. 检查文件是否正确生成
ls -la src/components/

# 2. 检查类型错误
npm run type-check

# 3. 检查lint
npm run lint

# 4. 运行项目
npm run dev
```

**提示**:
- 💡 生成后立即验证
- 💡 有问题可以修改改动点重新生成
- 💡 支持增量生成（只生成修改的部分）

### `/spec.test` - 生成测试代码

**用途**: 为生成的代码编写完整的测试

**使用场景**:
- ✅ 代码生成完成后
- ✅ 代码验证通过后
- ✅ 需要补充测试

**执行流程**:
```
1. 读取代码生成报告
2. 询问是否有人工测试用例
3. 为每个文件生成测试:
   - 单元测试: 纯函数、工具类
   - 组件测试: UI组件
   - 集成测试: 完整流程（可选）
4. 生成测试报告
```

**交互示例**:
```
AI: 是否有人工编写的测试用例作为参考？
用户: 没有 / [提供测试用例]

AI: 开始生成测试...
AI: ✅ src/components/Login.test.tsx
AI: ✅ src/api/auth.test.ts
AI: ✅ 测试生成完成
```

**产出文件**:
- 测试文件（`*.test.ts` / `*.test.tsx`）
- `.spec/feature/{date}/test-report.md`

**测试类型**:

**1. 单元测试**
```typescript
// src/utils/validation.test.ts
describe('validation', () => {
  test('validateEmail should return true for valid email', () => {
    expect(validateEmail('test@example.com')).toBe(true);
  });
});
```

**2. 组件测试**
```typescript
// src/components/Login.test.tsx
describe('Login', () => {
  test('should render login form', () => {
    render(<Login />);
    expect(screen.getByText('登录')).toBeInTheDocument();
  });
});
```

**3. 集成测试（可选）**
```typescript
// src/features/auth.test.ts
describe('Auth Flow', () => {
  test('should complete login flow', async () => {
    // 测试完整登录流程
  });
});
```

**运行测试**:
```bash
# 运行所有测试
npm test

# 运行指定测试
npm test Login.test

# 查看覆盖率
npm test -- --coverage
```

**提示**:
- 💡 提供人工用例能提高测试质量
- 💡 关注测试覆盖率（建议80%以上）
- 💡 复杂业务逻辑建议100%覆盖
- 💡 测试应该能正常运行

### `/spec.review` - 代码审查

**用途**: 多维度全面审查代码质量

**使用场景**:
- ✅ 测试通过后
- ✅ 修复问题后重新审查
- ✅ 追求更高质量

**执行流程**:
```
1. 读取代码生成报告
2. 并行启动3个审查Agent:
   - 规范性审查Agent
   - 安全性审查Agent
   - 性能审查Agent
3. 合并审查结果
4. 生成综合报告和评分
```

**示例**:
```
AI: 启动代码审查...
AI: 并行审查: 规范性、安全性、性能
AI: ━━━━━━━━━━━━━━━━━━━━━━━━━━━━
AI: ✅ 审查完成
AI:
AI: 📊 综合评分: 85/100
AI:
AI: 🔴 严重问题: 2个
AI: 🟡 警告: 5个
AI: 🔵 改进建议: 3个
AI:
AI: 详细报告: .spec/feature/{date}/code-review/
```

**产出文件**:
```
.spec/feature/{date}/code-review/
├── review-report.md         # 综合报告
├── compliance-review.md     # 规范性审查
├── security-review.md       # 安全性审查
└── performance-review.md    # 性能审查
```

**审查维度**:

**1. 规范性审查**
```
检查项:
✓ 命名规范
✓ 代码结构
✓ 注释完整性
✓ TypeScript类型
✓ 文件组织
✓ 统一的代码风格
```

**2. 安全性审查**
```
检查项:
✓ XSS漏洞
✓ SQL注入
✓ 敏感信息泄露
✓ 权限控制
✓ 输入验证
✓ CSRF防护
```

**3. 性能审查**
```
检查项:
✓ 不必要的重渲染
✓ 内存泄漏
✓ 大对象操作
✓ 循环性能
✓ 异步处理
✓ 资源加载优化
```

**问题等级**:
- 🔴 **严重**: 必须修复（安全漏洞、严重Bug）
- 🟡 **警告**: 建议修复（性能问题、规范问题）
- 🔵 **改进**: 可选优化（代码优化建议）

**处理建议**:
```
评分 90-100: 优秀，可以直接使用
评分 80-89:  良好，修复严重问题
评分 70-79:  及格，建议修复警告
评分 <70:    需要改进，重点修复
```

**提示**:
- 💡 重点关注🔴严重问题
- 💡 修复后可以重新审查
- 💡 追求85分以上
- 💡 可以忽略不合理的建议

### `/spec.archive` - 归档与知识库更新

**用途**: 归档需求并更新代码知识库

**使用场景**:
- ✅ 需求完成后
- ✅ 代码已合并到主分支
- ✅ 需要更新知识库

**执行流程**:
```
1. 读取所有阶段的文档
2. 生成归档总结:
   - 需求概要
   - 技术方案概要
   - 代码变更统计
   - 测试覆盖情况
   - 审查结果总结
   - 经验教训
3. 更新知识库:
   - 新增的组件/API/函数
   - 新的编码经验
   - 架构变更
4. 生成归档报告
```

**示例**:
```
AI: 开始归档...
AI: 生成归档总结
AI: 更新知识库
AI: - 新增 3 个组件
AI: - 新增 2 个API
AI: - 记录 1 条经验
AI: ✅ 归档完成
```

**产出文件**:
- `.spec/feature/{date}/archive-summary.md` - 归档总结
- 更新 `.spec/knowledge/` 下的知识库文件

**归档总结内容**:
```markdown
# 归档总结

## 需求概要
实现用户登录功能

## 技术方案
- 新建Login组件
- 添加auth API
- 修改路由配置

## 代码变更
- 新建文件: 3个
- 修改文件: 2个
- 新增依赖: axios

## 测试情况
- 测试文件: 5个
- 覆盖率: 85%

## 审查结果
- 综合评分: 85/100
- 严重问题: 0个
- 已全部修复

## 经验总结
- 登录状态使用localStorage存储
- 错误提示使用Toast组件
- API请求统一使用axios实例
```

**知识库更新**:
- 组件清单增加新组件
- API清单增加新接口
- 函数清单增加新函数
- 记录有价值的经验

**提示**:
- 💡 完成需求后立即归档
- 💡 保持知识库最新
- 💡 记录有价值的经验
- 💡 便于后续查找和复用

## 🔄 命令组合使用

### 标准完整流程

```bash
/spec.init              # 首次：初始化
  ↓
/spec.feat-prd          # 需求分析
  ↓
/spec.feat-tech         # 技术方案
  ↓
/spec.code              # 生成代码
  ↓
npm run dev             # 验证代码
  ↓
/spec.test              # 生成测试
  ↓
npm test                # 运行测试
  ↓
/spec.review            # 代码审查
  ↓
[修复问题]              # 如有严重问题
  ↓
/spec.archive           # 归档完成
```

### 快速流程（跳过测试和审查）

```bash
/spec.feat-prd
  ↓
/spec.feat-tech
  ↓
/spec.code
  ↓
npm run dev
  ↓
/spec.archive
```

**注意**: 不推荐跳过测试和审查

### 迭代优化流程

```bash
/spec.code              # 首次生成
  ↓
npm run dev             # 发现问题
  ↓
[修改改动点]            # 修改tech/modifications/
  ↓
/spec.code              # 重新生成
  ↓
npm run dev             # 再次验证
  ↓
/spec.review            # 审查
  ↓
[修复问题]
  ↓
/spec.review            # 再次审查
  ↓
/spec.archive           # 满意后归档
```

## 💡 使用技巧

### 1. 命令执行顺序

**必须顺序执行**:
- `/spec.init` → 其他命令（首次使用）
- `/spec.feat-prd` → `/spec.feat-tech` → `/spec.code`

**可以跳过**:
- `/spec.test` - 不推荐
- `/spec.review` - 不推荐

**可以重复**:
- `/spec.code` - 修改改动点后重新生成
- `/spec.review` - 修复问题后重新审查

### 2. 中途暂停和恢复

**暂停工作**:
```bash
# 按 Ctrl+D 或输入 exit 退出 Claude Code
exit
```

**恢复工作**:
```bash
# 重新启动 Claude Code
claude

# 继续执行下一步命令
/spec.feat-tech  # 如果你刚完成 /spec.feat-prd
```

所有数据都保存在 `.spec/feature/{date}/` 目录下

### 3. 查看生成的文档

```bash
# 查看需求目录
ls .spec/feature/$(date +%Y-%m-%d)/

# 查看需求文档
cat .spec/feature/*/prd/clarified/*.md

# 查看技术方案
cat .spec/feature/*/tech/tech-solution.md

# 查看代码生成报告
cat .spec/feature/*/code-generation-report.md

# 查看审查报告
cat .spec/feature/*/code-review/review-report.md
```

### 4. 修改和重新生成

**修改需求**:
```bash
# 编辑需求文档
vim .spec/feature/{date}/prd/clarified/req-1.md

# 重新生成技术方案
/spec.feat-tech
```

**修改技术方案**:
```bash
# 编辑改动点
vim .spec/feature/{date}/tech/modifications/new-Login.tsx.md

# 重新生成代码
/spec.code
```

### 5. 团队协作

**提交知识库**:
```bash
git add .spec/knowledge/
git commit -m "Update knowledge base"
git push
```

**分享需求文档**:
```bash
# 提交feature目录（可选）
git add .spec/feature/
git commit -m "Add feature: user login"
git push
```

## ❓ 常见问题

### 命令相关

**Q: 命令输入后没反应？**

A: 检查：
1. 命令拼写是否正确（区分大小写）
2. 是否在Claude Code环境中
3. 重启Claude Code

**Q: 可以自定义命令吗？**

A: 可以！编辑 `.claude/commands/` 目录下的文件

### 执行相关

**Q: 命令执行失败怎么办？**

A:
1. 查看错误信息
2. 检查前置条件是否满足
3. 重新执行命令
4. 如果持续失败，可以跳过该步骤

**Q: 可以中途取消吗？**

A: 可以，按 `Ctrl+C` 取消当前命令

### 文件相关

**Q: 知识库文件可以手动编辑吗？**

A: 可以，但建议通过 `/spec.init` 和 `/spec.archive` 自动维护

**Q: feature目录需要提交到Git吗？**

A: 可选，建议：
- 知识库提交（团队共享）
- feature目录可选（便于Review）
