# AI 应用工程实战方法论（草稿）

> 状态：草稿，边聊边改。本文从 my-turborepo 的真实开发经历提炼，不是教科书理论。
> 当前形态：**面试小抄**——给自己看，名词不展开，重在"怎么讲 + 为什么这么决策 + 追问怎么答"。

## 缘起：为什么要做这一切（面试开场总纲）

### 核心信念：AI 不可信，可信度必须锚定在 AI 之外

我做这一切的底层信念只有一句：**AI 是不可信的——幻觉不是 bug，是它的本质，永远存在。**
所以**可信度不能寄生在 AI 自己身上，必须锚定在 AI 之外的确定性上**：要么是真实的代码规则
（确定的事实），要么是一套极致收敛、宁缺毋滥的数据/评分机制。

我所有的工作都是这一个信念的不同侧面：
- 不信 AI 的输出 → 用 **Eval** 量化它（不靠感觉）
- 不信打分的 AI（judge）→ 做 **校准**（不靠 judge 自说自话）
- 不信模型记得的东西 → 建 **记忆系统**，且每条记忆带 `source` 可追溯
- 不信模型的语义判断（实测 Kappa=0）→ **宁可冗余也不让它自动决定**

### 触发痛点：一次改 prompt 的"按下葫芦浮起瓢"

这个信念不是凭空来的，是被一个具体痛点逼出来的。最开始我"头痛医头"，遇到问题就改 prompt。
直到撞上这件事——

我的 agent 有多个工具（查天气、建待办、查记忆…），模型靠每个工具的描述（本质就是 prompt）
决定调哪个。有次为了让它更准识别"建待办"，我把 create_reminder 的描述写得更主动、更宽泛。
当前场景好了，但我立刻意识到：**工具描述之间是相互竞争的**——把"建待办"写强了，模型很可能在
用户只是闲聊、或本该查天气时也误调它。我改的是一个工具的 prompt，影响的是整个工具选择的平衡。
**而我当时没有任何手段验证这件事**，只能自己想几个例子手动试，试不全。

由此看清三层递进的问题：
1. **改 prompt 只保当前场景，无法验证对其他场景的影响** → 催生 **Eval**：把全局影响变成固定用例上可量化、可对比的数字。
2. **就算有打分，打分用的 judge 自己也是会出错的 AI，可信吗** → 催生 **校准**：先证明打分器准不准。
3. **验证中暴露模型会编瞎话、会记错** → 催生 **记忆系统 + 反幻觉规则**。

### 准则"宁缺毋滥"——以及它的边界

约束这个不可信 AI 的操作准则是**宁缺毋滥**：judge 不可信宁可不用它做硬决策、inferred 拿不准
宁可不存、改vs增判不准宁可冗余也不误删。它的反面"宁滥毋缺"（能存就存、像就信）正是幻觉的温床。

**但宁缺毋滥不是教条，是场景决定的。** 判据是：**这个场景里"错"和"漏"哪个代价更大。**
- 错的代价 >> 漏的代价（健康/过敏、待办时间、用户身份、记忆写入）→ 宁缺毋滥。
- 漏的代价 >> 错的代价（创意发散、闲聊陪伴）→ 反而该放开，太保守就没用了。

我的项目大量落在前者，所以自然采用宁缺毋滥；但我清楚它只在"错代价大于漏代价"时成立。

### 跨领域佐证：这不是 AI 独有

这套"宁缺毋滥"的判断不是 AI 专属。我做过金融结算类系统——逻辑一模一样：一笔账**算错**（滥）
要人工追溯对账、代价极高；一笔账**暂时卡住等复核**（缺）代价可控。所以结算系统天然宁可卡住
等人工确认，也不能算错自动放过——和"inferred 宁可不存""改vs增宁可冗余"是同一个决策结构。

**一句话**：我是用做金融结算的严谨度（一切可追溯、不靠"差不多"），来约束一个天生爱猜的 AI。
传统软件追求"正确"；AI 应用追求的是**"在不确定性里建立可信度"**——Eval、校准、记忆、规则，
都是在回答同一个问题：怎么让一个不确定的系统，变得可信、可控、可持续改进。

## 0. 一句话定位

这套方法论是关于**"不碰模型权重，怎么把第三方/本地模型用好、用对、用得可信"**。
不涉及微调（改权重）；涉及的是 prompt 工程、决策规则设计、和质量评估三件事的配合。

## 0.1 三条路的分工（先分清自己在做哪件事）

| 问题 | 解法 | 本项目 |
|---|---|---|
| 模型不够聪明/不会用工具 | 换更强模型 or prompt 工程 | ✅ |
| 模型不知道某些私有知识/事实 | RAG（检索增强） | （OnYour 项目） |
| 模型不会按特定风格/格式/技能做 | 微调（改权重） | ❌ 未用，也不需要 |

**判断口诀**：补"知道什么"用 RAG，调"怎么做"才考虑微调，能用 prompt/规则解决的都不上微调。

## 策略 A：Eval（把"好不好"变成数字）

**核心原则：把"答得好不好"拆成可度量的维度，能用代码断言的绝不用模型判。**

### A0. 全局总览（两张图先建立认知）

**图一：一次 eval 的完整流程**——eval 是"考试"，客观题代码判、主观题 judge 判。

```

                              ▼
                    ┌──────────────────┐
                    │   跑 Eval（考试）  │  ← 一组固定用例（考卷）
                    └──────────────────┘
                              │
                  每条用例 agent 跑一遍，产出：
                  ① 调了哪些工具+参数(trace)  ② 回复文本
                              │
              ┌───────────────┴───────────────┐
              ▼                                 ▼
   ┌──────────────────────┐        ┌────────────────────────┐
   │  有标准答案的题        │        │  没标准答案的题          │
   │ (工具选对没/参数对没)  │        │ (回复好不好/有没有幻觉)  │
   └──────────────────────┘        └────────────────────────┘
              │                                 │

   ┌──────────────────────┐        ┌────────────────────────┐

                              │
                              ▼
                对比改 prompt 前后 → 有没有改坏别的？
```

```

   (我说了算·            同一批                 (算 Kappa，
    金标准·无AI)                               扣掉瞎蒙运气)
         └────────────────────┼────────────────────┘
```

> **一句话**：eval 是考试，客观题代码判、主观题 judge 判；judge 这个"判卷 AI"默认不可信，
> 必须人工校准测一遍——可信的才用（quality），瞎蒙的就弃（faithfulness）。**人始终是最后的标准。**

### A1. 能用代码断言的，绝不用模型判

**怎么讲**：eval 我分两类维度。「该不该调某工具、参数对不对」这种有唯一正确答案的，直接用代码
断言（对比 trace 里的工具名和参数）——零成本、每次结果一样、完全可信，是 eval 的地基。只有
「回复质量、有没有幻觉」这种没标准答案的，才动用 LLM-judge。**有唯一答案的绝不浪费一次模型调用去判。**

### A2. LLM-judge 必须先校准再信——只看一致率会被骗

**怎么讲（30秒版）**：我用 LLM 给 agent 的回答打分（judge）。但我没直接信它，而是做了校准——
自己人工标一批金标准，让 judge 判同一批，对比。发现 faithfulness 的一致率 83% 看着不错，
**但 Cohen's Kappa = 0**，说明这 83% 全是"大部分样本本就无幻觉"撑的，judge 没有真判别力。
报告里那"4 次幻觉"，3 次是误判。**没校准就会拿假数据优化假问题。**

**决策链（为什么这么做）**：质量/幻觉没有标准答案，只能用 LLM-judge；但 judge 本身也会错，
所以不能直接信 → 引入校准；校准时发现只看一致率会被高 TN 占比骗 → 改看 Kappa。

**追问怎么答**：
- Q：*为什么不直接信 judge 的分？* → judge 是模型，一样会幻觉/有偏好；它和被测是同家模型，还有自我偏袒。
- Q：*Kappa=0 一致率却 83%，矛盾吗？* → 不矛盾。一致率含"瞎蒙也对"的部分，样本里 95% 无幻觉时，
  全填"无幻觉"就有 95% 一致率。Kappa 扣掉运气基线，0 就是"等于瞎蒙"。
- Q：*那 faithfulness judge 你最后怎么处理？* → 标记为不可信、不参与硬决策，留作信号；改用确定性更高的维度做决策（见 B2）。

### A3. 小样本通过率会骗人，eval 通过 ≠ 端到端没问题

**怎么讲（30秒版）**："我朋友老王对海鲜过敏"这条（无关第三方，不该存），抽取器 eval 跑了 30 次
全部正确判"不存"，看着稳如磐石。可一起真服务真聊，它偶发就存进去一次。同一输入、同样
temperature=0，eval 不存、真聊存了。**30/30 的满分给了我虚假安全感，eval 的有限样本盖不住低频非确定性。**

**决策链**：eval 是隔离的、单点的、受控输入 → 它验证"单次判断在干净条件下对不对"，但盖不住
"多路径叠加、状态污染、低频翻车" → 所以 eval 之外必须再做端到端真聊，两者盲区互补。

**追问怎么答**：
- Q：*temperature=0 不是确定的吗，怎么还翻车？* → temp=0 只是降低随机，不等于完全确定；
  且真实链路的上下文、历史和 eval 的隔离输入不同，行为会变。
- Q：*那 eval 还有什么意义？* → eval 管"改 prompt 后全局回归"（快速、可量化、防止改 A 坏 B），
  真聊管"集成后的真实行为"。一个防回归、一个抓集成 bug，不能互相替代。
- Q：*真聊抓到过什么 eval 没抓到的？* → 双写（两条写入路径叠加）、召回漏数据、会话历史掩盖召回真实状态——全是隔离 eval 结构上发现不了的。

### A4. eval 抓的是单测抓不到的"模型行为缺陷"

**怎么讲**：单元测试全绿，但 create_reminder 建出来的待办时间是空的。单测为什么没抓到？因为它用
mock 模型、硬编码参数，参数永远"对"。只有 eval 用真模型跑，才暴露真模型把 schema 字段 `todoTime`
自作主张传成了 `time`。**单测验"代码对不对"，eval 验"模型行为对不对"——后者是前者结构上的盲区。**

### A5. 测试你的测试

**怎么讲**：评分器（算一致率、Kappa、参数匹配）自己也是代码、也会写错。所以给评分器写了
`selftest`，用构造的假数据验证它判得对。**评估别人之前，先证明评估工具自己是对的。**

## 策略 B：行为调优（prompt + 决策规则，非微调）

**核心原则：用数据驱动调 prompt 和决策逻辑，不拍脑袋；prompt 能解决的不上微调。**

| 规则 | 来源 |
|---|---|
| 改 prompt 之前先用 eval 量化现状，知道差在哪个维度。 | value 测出 57% 才动手 |
| **决策依赖的维度，必须是 eval 实测可靠的**。 | value 57% 不可靠 → 改用 confidence(100%) 驱动 |
| 调"用哪个维度做决策"比调"维度判得多准"更关键。 | confidence 比 value 更贴反幻觉 |
| 低频非确定性翻车，用 prompt 加显式反例锚点（few-shot）压低。 | 老王误存 → prompt 补反例 |
| prompt/规则能解决的不上微调（微调成本高、迭代慢、黑箱；且第三方 API 常无权重可调）。 | 全程未用微调 |

## 策略 C：规则编制（规则从真实例子撞出来）

**核心原则：规则从具体例子里"撞"出来，对不确定的保守处理，宁冗余不误删。**

| 规则 | 来源 |
|---|---|
| 设计前先走具体例子，空想覆盖不全。 | 走 11 例撞出 6 个设计缺口 |
| 一个规则只覆盖一个场景时，要穷举同类的其它情况。 | 路 C 把多过敏误当新旧版本 |
| **不可靠的判断不要自动化**：宁可冗余（返回全部），不可误删。 | "改 vs 增"靠模型判 Kappa=0 → 返回全部 |
| 改/加路径前先盘点已有路径和现成范式。 | 双写 bug、createdAt 用错类型 |
| 高风险操作设默认安全态（拿不准一律降级/确认）。 | inferred 绝不静默写入 |

---

## 串起来的工作流

> 用 eval 把"好不好"变数字 → 校准 eval 自己可不可信 → 用数字驱动调 prompt/规则（非微调）
> → 规则从真实例子撞出来、对不确定的保守处理 → 真聊验证 eval 的盲区。

每一步都让数据/例子说话，而不是"我调了调感觉好多了"。这是 AI 应用工程师区别于调包侠的地方。
