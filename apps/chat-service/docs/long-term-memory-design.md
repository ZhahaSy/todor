# 长期记忆系统 — 设计文档（评分与数据模型）

> 状态：设计阶段，未实现。本文只定"宪法"（数据模型 + 评分规则），实现分期另议。
> 目标：让助手"越用越懂我"，同时**用规则框定写入**，避免自由记忆野蛮生长引入幻觉。

## 0. 一句话定位

长期记忆 = 跨会话持久的、关于用户的事实。它是**对抗幻觉的数据地基**：
模型不该猜的信息，前提是"它本来有地方查"。没有记忆层，约束模型也只能让它答"不知道"。

## 1. 三层记忆的边界（务必分清，否则会打架）

本项目已存在两层，本设计新增第三层。三者职责严格不重叠：

| 层 | 载体 | 存什么 | 生命周期 | 现状 |
|---|---|---|---|---|
| **短期对话记忆** | Redis（`RedisChatMemory`） | 最近 k 轮对话上下文 | 滑动窗口，2h 过期 | ✅ 已有 |
| **结构化档案** | SQLite `User` 实体 | 稳定核心字段：住址/职业/作息/爱好 | 永久，低频变化 | ⚠️ 字段已有，但对话读不全、改不了 |
| **自由记忆**（新） | SQLite 新表 `user_memory` | User 表装不下的动态事实：过敏/偏好/关系/目标 | 永久，可更新/失效 | ❌ 待建 |

**关键认知**：你纠结的"结构化 vs 自由"，在本项目里天然就是后两层的分工——
固定且已知的进 `User` 字段，动态长出来的进 `user_memory`。不必二选一。

边界规则：
- 短期记忆**永不**晋升为长期（它会过期，是对话流，不是事实）。
- 长期记忆的写入由"评分"决定（见 §3），不是每句话都进。
- 读取时：短期记忆走原有 system prompt 注入；长期记忆走**召回工具/按需注入**（见 §4）。

## 1.5 记忆 vs Todo 系统的边界（走例子撞出）

你已有 `todo` 表。记忆和待办容易混，必须划清，否则同一件事两张表都存 = 数据重复 + 冲突源。

- **单条待办不进记忆**：有时间点、要触发提醒、做完就结束的事件（"下周一给猫打疫苗"）→ 进 `todo`，
  **不复制**到 user_memory。原则仍是"同一件事只有一个权威存储位置"。
- **一句话可同时触发两个动作**："记一下，我家猫叫咪，下周一打疫苗" → "猫叫咪"进 user_memory
  （稳定事实），"打疫苗"进 todo（事件）。抽取与待办创建不是二选一，可并行。
- **判据**：有明确终点、做完即结束 → todo；没有终点、用来理解用户是什么样的人 → memory。
  "猫要打疫苗"打完结束（todo）；"用户养了只猫"永远成立（memory）。

### 多源记忆（未来扩展，第一~三期都不做）

记忆来源不止对话。**todo 历史聚合出的"模式"也是记忆**：反复建健身待办 → "有健身习惯"；
待办总设在深夜 → "习惯晚上处理事情"。这是从 N 条待办**归纳**出的模式记忆，不同于从对话提取单条事实。
- 列为未来"多源记忆"扩展。**第一~三期不碰**，理由：①技术更难（聚合/归纳，易过度概括成幻觉）；
  ②依赖单源（对话提取）先跑通；③要先摸清现有 todo 数据形态。先把"对话→事实记忆"这一条路径做扎实。

## 2. 自由记忆的数据模型（半结构化）

不是纯自由文本（无法过滤/去重），也不是死板表单（太僵）。而是
**自由 content + 受控元数据**。`user_memory` 表：

| 字段 | 类型 | 作用 | 反幻觉意义 |
|---|---|---|---|
| `id` | uuid | 主键 | |
| `userId` | varchar, 索引 | 归属（沿用现有 userId 鉴权范式） | 隔离他人记忆 |
| `subject` | varchar | 这条记忆**关于谁**：`self` / 关系人或宠物名（如"父亲"、"猫:咪"） | 区分用户本人 vs 关系人 vs 无关第三方；无关第三方不入库 |
| `content` | text | 记忆正文，自由文本 | 灵活，不僵化 |
| `category` | enum | 受控分类（见下） | 召回时按需过滤，避免全量噪声 |
| `temporality` | enum: `permanent`/`temporal` | 永久属性 vs 有时限的状态 | 时限型可失效，避免过期事实当永久用 |
| `expiresHint` | varchar, null | 软性失效线索（如"2025-12"、"考研后"） | 召回时若已过线索则降权/标注"可能过期"，**不硬删** |
| `confidence` | enum: `stated`/`inferred` | 用户明说 vs 模型推测 | **命门**：推测的不能当事实用 |
| `sensitivity` | enum: `normal`/`sensitive` | 是否健康/财务/隐私类敏感信息 | 敏感信息召回需更克制、时效更短、可被遗忘 |
| `source` | text | 来源原话，如"用户:我对花生过敏" | **命门**：召回时连证据一起给模型，可追溯 |
| `status` | enum: `active`/`superseded`/`deleted` | 活跃/被取代/被用户删除 | 召回只取 active；deleted 是用户主动遗忘 |
| `supersededBy` | uuid, null | 被哪条取代 | 冲突更新链路 |
| `createdAt`/`updatedAt` | datetime | 时间戳 | 时效判断、按新鲜度排序 |

**`category` 受控枚举**（起步集，可扩展）：
`health`(健康/过敏)、`preference`(偏好/口味)、`relationship`(人际)、
`goal`(目标/计划)、`profile_extra`(档案补充)、`other`。

**两个"命门"字段的意义**——它们让自由记忆和"工具返回数据"一样可信、可追溯：
- `source`：召回时模型看到的不只是结论"对花生过敏"，还有原话依据。等于给记忆带了出处。
- `confidence`：`inferred`（模型推测）的记忆，召回时应提示模型"这是推测，不确定"，
  甚至默认不静默写入（走二次确认）。**低确信绝不冒充事实**，这是反幻觉的核心约束。

**`subject`（关于谁）—— 走例子撞出的字段**：记忆主体不一定是用户本人。
- `self`：用户自己的事实（"我对花生过敏"）→ 可记。
- 关系人/宠物：用户重要关系网里的（"父亲对花生过敏"、"猫叫咪"）→ 可记，subject 记成"父亲"/"猫:咪"。
- 无关第三方（"我朋友老王对海鲜过敏"）→ **不入库**，留在对话流里自然过期。
- subject 参与"要不要记"的判断：self/关系人值得记，无关第三方不记。

**时效性（`temporality` + `expiresHint`）—— 走例子撞出的维度**：记忆有两种寿命。
- `permanent`：永久属性（过敏、籍贯、性格），除非被推翻一直有效。
- `temporal`：有时限的状态（"在准备12月考研"、"在减肥"），有自然失效点。
- **不用数据库 TTL 硬删**（万一用户延期了呢，误删比过期更糟）。而是记一个软性
  `expiresHint`，召回时若已过线索则**降权/标注"可能已过期"**，真正失效交给冲突更新顶替。

**敏感度（`sensitivity`）—— 走例子撞出，最易伤害信任的维度**：健康/财务/隐私类信息
（"下月做手术"、"在吃抗抑郁药"）即使合格该记，对待方式也和"喜欢美式"完全不同：
- **长期留存风险**：手术是短期状态，康复后模型还召回"你身体没好吧"是冒犯。敏感+temporal 尤其要主动过期。
- **召回克制**：健康隐私不该在不相关对话里被带出（问午饭吃啥，别提手术）。
- **可遗忘**：用户能说"别记我的健康信息"。
- **第一期策略**：先加 `sensitivity` 字段**标记**（便宜，避免敏感信息和普通偏好一视同仁）；
  "召回克制、主动过期、可遗忘"等**治理行为留到后续**（完整治理是大工程，第一期做不完）。

### 与 User 结构化档案的路由

**已拍板：User 表固定 schema，不为对话记忆扩字段。** 一条新事实怎么路由：
- **仅当**命中 User **已有**字段的明确语义（address/job/schedule/hobby/age/gender）→ 更新该字段。
  例："我搬到上海了"→address；"换工作去字节"→job；"习惯晚睡"→schedule。
- **其余一切细粒度偏好/事实全进 `user_memory`**，按 category 归类。
  例："喜欢喝美式"→ user_memory(preference)，**不塞 hobby**——hobby 是单值字段会互相覆盖，
  且把多类语义倒进一栏会变杂物筐。多样性交给一行一条、带 category 的记忆表。
- 判据口诀：**User 表只接"身份证上印着的那几栏"的直接更新，其余统进记忆表。**
- 牵强匹配（把"咖啡偏好"硬归 hobby）是脏数据来源，宁可进 user_memory。
- 这条路由判断由抽取环节的模型 + 规则完成（见 §3 的 routeToUserField）。

## 3. 评分模型（写入的"宪法"）

写入不是二元的"存/不存"，是置信度问题。每条候选记忆打一个分，分级处理。
**评分不是一个笼统的黑箱分，而是两个正交维度相乘**，这样规则可解释：

### 两个维度

**A. 价值（value）**：这条信息是否稳定、关于用户、未来用得上？
- 高：长期属性/偏好/约束（过敏、忌口、长期目标、重要关系）
- 低：一次性、时效性、情绪（"今天好累"、"刚吃了饭"、"这周末有事"）

**B. 确信（confidence）**：用户明确陈述，还是模型推测？
- `stated`：用户原话直接断言（"我对花生过敏"）
- `inferred`：模型从上下文推测（"他好像不爱加班"）

### 分级动作（confidence 驱动 —— 2026-06-22 经 eval 实测修正）

> **原方案是"value 驱动"（高价值静默存、中价值二次确认）。但 `pnpm eval:memory` 实测：
> 抽取器 value 准确率仅 57%（系统性偏高），而 confidence 准确率 100%、shouldRemember 100%。
> 用 57% 的维度做"静默存 vs 二次确认"的硬决策会频繁判错档位，且偏高倾向正好会把本该
> 确认的误判成静默存——踩中"未经确认就写库"的红线。故改为 confidence 驱动。**

决策只依赖两个 eval 实测 100% 可靠的维度：`shouldRemember` 和 `confidence`：

| shouldRemember | confidence | 动作 |
|---|---|---|
| false | — | 不存 |
| true | `stated`（用户明说） | **直接静默写入** |
| true | `inferred`（模型推测） | **非阻塞二次确认**（推测是幻觉源头，绝不静默入库） |

为什么 confidence 驱动更对（不只是绕开短板）：幻觉的根源是"模型猜的被当事实存"，
而 confidence 正是"是不是猜的"这一维度——用它当存/问的闸门，直接命中反幻觉要害。

**value 降级为召回参考**：不再参与"存还是问"的硬决策，只在召回排序时让高价值记忆优先
（判错也不会导致未确认写库这种严重后果）。

代价与兜底：confidence 驱动会让"用户明说但低价值"的话也直接存（如"今天中午吃了沙县"）。
但 `shouldRemember`（100% 准）那道闸会先把这类低价值判成不记，根本到不了写入；
真漏网了用户也能"别记了"删除。即 **shouldRemember + confidence 两道准闸联合把关，value 不参与硬决策**。

**核心约束（呼应你最担心的）**：`inferred` 的记忆**绝不静默写入**，必须经二次确认或不存。
低价值的不存，但永远提供"记住"能力（用户显式指令可越过评分直接存）。

### 三个动作的落地形态

- **高分静默存**：抽取后直接 upsert，不打断对话。
- **中分二次确认（不打断主对话）**：主对话照常回复，**额外**产出一个非阻塞的待确认项
  （侧边栏/记忆中心列表，或一张可点的卡片）。这一环与 GenUI 是天然结合点。
- **低分 + 显式指令**：用户说"记一下…"→ 越过评分，强制写入（confidence 记为 stated）。

### 评分由谁打

抽取环节用一次轻量 LLM 调用 + 规则后处理：输入是"用户最新消息（+少量上下文）"，
输出结构化：
```
{ shouldRemember, value, confidence, category,
  subject,            // self / 关系人名 / 宠物名；无关第三方 → shouldRemember:false
  temporality,        // permanent | temporal
  expiresHint?,       // temporal 时的软失效线索
  content, source,
  routeToUserField?   // 命中 User 字段语义则填字段名，否则 null（走 user_memory）
}
```
**这个抽取器本身要进 eval**——用例如"我对花生过敏"应 high/stated/health/self/permanent，
"今天好累"应 shouldRemember:false，"老王对海鲜过敏"应 shouldRemember:false（无关第三方）。
否则抽取规则无从验证，又变回野蛮生长。

## 4. 召回（读取时取哪些记忆）

**幻觉的真正来源不是"记了自由文本"，而是召回了不相关/已过期的记忆。** 所以规则下在这里：

- **只取 `status='active'`**：被取代的记忆不进上下文。
- **category 过滤 + 相关性**：问吃饭取 `health`/`preference`，别把全部记忆塞进去。
  起步阶段记忆量小（几十条），可"全量 active 注入"；量大后再上关键词/向量检索。
- **召回时连 `source` 一起给模型**：让模型基于"有出处的记忆"作答，而非凭空。
- **`inferred` 记忆要标注不确定**：注入时附"（推测）"，模型措辞需留余地。
- 召回入口用**工具**（`recall_memory`，模仿现有 `get_user_info` 范式），
  或在 system prompt 注入精选记忆。二者取舍见 §7 开放问题。

## 5. 冲突与更新（最易被忽略、最易生幻觉的一环）

用户上周说"爱喝咖啡"，这周说"戒咖啡了"——野蛮系统会两条都留，模型随机引用一条 → 幻觉。

规则：
- 写入新记忆时，先在**同 userId + 同 category** 下找语义冲突的旧记忆。
- 命中冲突 → 旧记忆 `status='superseded'`、`supersededBy=新id`，新记忆 `active`。
- 不直接物理删除（保留历史，可追溯"用户改过主意"）。
- 冲突检测起步可用简单规则（同 category 下高相似），后期可上更强的语义比对。
- **这是 Mem0 等系统最核心的难点**，起步阶段可先做保守版（只在明显冲突时覆盖，
  拿不准就并存 + 标注时间，让召回优先取最新）。

### 第一期的冲突方案 = 路 C（已拍板）

第一期**不让模型判断"两条算不算冲突"**（语义冲突判断依赖模型可靠性，而校准已证明
本模型 judge 类任务 Kappa=0，不可靠）。改用一条笨但安全的召回规则绕开：

> **召回时，同 `subject` + 同 `category` 只取 `createdAt` 最新的一条。**

- 旧记忆不物理删、也不在写入时判作废，只是召回时被新的盖住。
- 例4（"以前过敏，脱敏好了"）：用户显式说"现在能吃芒果"→ 新记忆入库；召回"健康+self"
  时只取最新 → 模型看到"能吃芒果"，看不到旧的"过敏"。**用召回规则规避冲突，而非写入时判冲突。**
- 完整的语义冲突检测（supersede 链路）仍留第三期。

## 6. 实现分期（每期独立可验证，eval 全程兜底）

- **第一期（地基）**：`user_memory` 表 + 三个对称操作：**显式写入 / 召回 / 显式删除**。
  - 写入：用户显式"记一下…"才存（无需评分）。
  - 召回：`recall_memory` 工具 + 同 subject+category 取最新（路 C）。
  - 删除：用户"别记 XX 了"→ 对应记忆标 `deleted`/不再召回（存删对称，敏感信息能撤回，建立信任）。
  - eval 验证："存了过敏，问吃啥，模型基于记忆答且不编"；"说别记了，之后召回不再出现"。
- **第二期（智能写入）**：加抽取器 + 评分（价值×确信）+ 高分自动存。
  **前置硬条件**：抽取器/评分必须先在第一期作为 eval 目标验证过准确率（造分类用例、
  断言 value/confidence/category 判得对），达标后才开"高分静默写入"的闸。
  理由：校准已证明本模型（v4-flash）schema 遵循不稳、judge Kappa=0，
  未经验证就让模型自动决定写入用户永久档案，脏数据会成为持续幻觉源，比不记更糟。
  eval 验证：抽取器分级准不准、会不会误存低价值/推测内容。
- **第三期（确认 + 冲突）**：非阻塞二次确认 UI（接 GenUI）+ 冲突更新（supersede）。
  eval 验证：改主意后模型引用最新事实、不引用过期的。
- **可选第四期**：召回升级为向量检索（记忆量大时）；接入 §1 的 User 字段双向同步。

**为什么这样分**：第一期就把 eval 一起做，每加一层都有回归兜底，不会越做越乱——
这是前期投资 eval 的复利。也呼应 privacy-01 的教训：记忆存在后，
"你记得我XX吗"才能真正基于数据回答，而非靠 system prompt 兜底或模型猜。

## 7. 待拍板的开放问题

### 已拍板（2026-06-22）
- **第一期写入范围 = 仅"用户显式指令"**（不上自动写入）。抽取器/评分先作为第一期
  eval 目标验证准确率，达标后第二期才开自动写入。理由见 §6。
- **召回入口 = 工具优先**（`recall_memory`，与 `get_user_info` 一致）；高频核心事实可常驻注入。
- **User 表固定 schema，不为对话记忆扩字段**。仅已有字段（address/job/schedule/hobby…）接对话更新，
  其余细粒度偏好全进 user_memory。见 §2 路由。
- **第一期冲突 = 路 C**（召回取最新规避，不让模型判冲突）。见 §5。
